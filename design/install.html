Prepare the Superset instance

Confirm the destination runs official Superset 6.1.0 and uses the existing client PostgreSQL connection. Then make these two settings explicit in the production superset_config.py.

1. Required for the dashboard's date queries

Add ENABLE_TEMPLATE_PROCESSING to the instance's existing FEATURE_FLAGS dictionary. Preserve every other feature flag already present:

FEATURE_FLAGS = {
    # retain the instance's other existing feature flags
    "ENABLE_TEMPLATE_PROCESSING": True,
}

The saved virtual datasets use Superset's built-in get_time_filter, filter_values and time_grain template values. Without this setting, the delivered date-range and Month/Quarter/Year query logic will not run. No custom template function is required. See the official Superset 6.1.0 SQL templating documentation.

2. Required only for the agreed short Time Unit menu

On a dedicated CSiM instance, add the tested denylist below so users see the relevant Month, Quarter and Year choices instead of seconds, minutes, hours, days and weeks:

TIME_GRAIN_DENYLIST = [
    "PT1S", "PT5S", "PT30S",
    "PT1M", "PT5M", "PT10M", "PT15M", "PT30M",
    "PT1H", "PT6H", "P1D", "P1W",
    "P1W/1970-01-03T00:00:00Z",
    "P1W/1970-01-04T00:00:00Z",
]

This menu setting applies to the whole Superset instance. It is appropriate for the dedicated CSiM installation. On a shared instance, review other dashboards before adding it. Omitting it leaves extra Time Unit choices visible; it does not remove the dashboard's date-range calculations.

Restart every Superset web process and background worker that loads superset_config.py after changing the file. If both settings are already present, leave them in place and restart only if the file was changed.

No custom Superset build is required. The date behavior, labels, missing-period rows, filter scopes and saved defaults are in the released dashboard, chart and dataset definitions. The production configuration enables those definitions and limits the instance-wide menu.

Update the existing dashboard

  1. Pause dashboard editing and back up the destination

    Export the current client dashboard with its charts and datasets. Also take a Superset metadata-database backup using the client's established procedure. If the export contains edits newer than the September source, reconcile them before continuing.

  2. Check out the exact installer

    Use the tested source revision. The dashboard ZIP by itself is provided for inspection and checksum comparison; it is not the supported update command.

    git clone https://github.com/DIGI-UW/csim.git
cd csim
git checkout d6351d954d5f265e0c0c3c5f66dbb96d612b5352

  3. Point the helper at client Superset

    Run these commands in the Python environment where Superset 6.1.0 and its dependencies are installed. Use the destination service URL and an administrator account:

    export CSIM_PROJECT_ROOT="$PWD"
export CSIM_SUPERSET_URL="https://CLIENT-SUPERSET-HOST"
export CSIM_SUPERSET_USERNAME="ADMIN-USERNAME"
export CSIM_ADMIN_PASSWORD="ADMIN-PASSWORD"

python scripts/dashboard_import.py import --profile client-update

    The helper updates the existing objects through Superset's asset API, excludes the database definition, and repairs the internal chart references and saved filter scopes for the destination instance.

  4. Compare the installed definitions

    python scripts/verify_import.py --profile client-update

    This compares the destination's saved SQL, calculated columns, measures, charts, colors, layout, filters and contents links with the versioned release.

Do not upload the ZIP through Superset's manual import screen. That skips the destination-reference repair. Do not import the public demo dashboard; its object identifiers belong to a different installation.

Confirm the update loaded

The definition comparison should finish successfully. Open the familiar dashboard and confirm that it is still connected to the client's data, that no duplicate CSiM dashboard or reporting datasets were created, and that an explicit date range works with Month, Quarter and Year.

Rollback

If the destination differs unexpectedly, stop before further edits and use the rollback already rehearsed against the client copy. Re-import the fresh pre-installation asset export. If that does not restore the relationships, restore the complete Superset metadata-database backup using the client's established recovery procedure.

A full metadata restore affects other Superset changes made after the backup, so schedule the installation without concurrent dashboard editing. Reporting records stay in PostgreSQL and should not be restored or replaced as part of this definition rollback.

After rollback, repeat the known hospital, date, total and filter checks. A dashboard that opens successfully is not enough to prove every relationship was restored.

Known limits and decisions

  • Clear all: official Superset 6.1.0 can retain a stale selection after Clear all and reselect. Reload after using Clear all. This package documents the limitation; it does not add a Superset patch.
  • Importer helper: the versioned helper is part of the tested installation path. It omits the database object and repairs destination references. A manual ZIP upload is not a supported installation path.
  • Time Unit choices: the short Month/Quarter/Year menu comes from the installation-wide TIME_GRAIN_DENYLIST shown above. It is not stored in the dashboard ZIP.
  • Supporting records view: the separate Data & records package still needs destination installation and role checks if the client accepts that workflow.
