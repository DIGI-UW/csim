What this update changes

UpdatesThe existing Individual Data dashboard, 21 chart definitions, six saved reporting-query definitions, layout, colors, filters and Table of Contents links.
PreservesThe client's dashboard identity, six reporting-dataset identities, PostgreSQL connection object, source-table names and uploaded Current, Historical and hospital-lookup records.
Does not includeA database connection definition, database credentials, reporting records, example dashboards, retired experiments, archived client datasets or a Superset application patch.
Separate supporting viewThe Data & records dashboard and individual-record review table remain a separate package. Installing the main update cannot silently add them to the familiar dashboard.

Dashboard definitions and reporting records are separate. This bundle describes what Superset should display and how it calculates results. It does not carry the rows stored in PostgreSQL. The tested helper also omits the database connection object from the update request.

Before installing

  1. Confirm the destination is the intended official Superset 6.1.0 instance.
  2. Export a fresh backup of the destination dashboard with its charts and datasets. Take a complete Superset metadata-database backup using the client's established backup procedure.
  3. Compare that export with the September baseline. If anyone saved later SQL, chart, layout or filter edits, reconcile them before continuing.
  4. Confirm the destination database, dashboard and six reporting datasets have the UUIDs listed in dashboard/client-update/manifest.json.
  5. Record one known hospital, reporting month and total, then verify that the existing PostgreSQL connection succeeds.
  6. Rehearse the complete import and rollback in a copy of the client Superset metadata before updating the live dashboard.

Do not use Superset's manual ZIP-upload screen for this update. The tested path uses the versioned helper so the database connection is omitted and destination chart references are repaired. The public demo dashboard also has different object identities and must not be imported into client production.

Installation sequence

  1. Keep the fresh backup

    Record the current destination revision and retain its exported definitions and metadata backup.

  2. Import the client update

    Use the versioned repository importer with the client-update profile. It sends a sparse update through Superset's asset API without a database definition, then corrects internal chart references and saved filter scopes that can otherwise retain numbers from the source instance.

  3. Run the definition check

    The verifier compares SQL, calculated columns, measures, chart settings, colors, layout, filter defaults and scopes, and all nine Table of Contents links with the tested release.

  4. Open and review the dashboard

    Check a known hospital and explicit date range before the updated dashboard becomes the accepted client release.

Administrator environment, commands and why the helper is required

These are commands for the destination's Superset Python environment, not a general workstation shell. Check out the exact release revision and make it readable inside that environment. Set CSIM_PROJECT_ROOT to that checkout, CSIM_SUPERSET_URL to the Superset service's internal URL, CSIM_SUPERSET_USERNAME to an administrator account, and CSIM_ADMIN_PASSWORD to that account's password. Then run:

python scripts/dashboard_import.py import --profile client-update
python scripts/verify_import.py --profile client-update

The client-update path does not require the PostgreSQL password because it does not import a database object. Superset assigns local numeric chart identifiers on each instance, and official 6.1.0 can retain source-instance numbers in saved dashboard references. The helper derives replacements from stable UUIDs and the destination objects; it does not patch or replace Superset.

Use the downloaded asset bundle for inspection and checksum comparison. The tested installation is the helper-driven path above.

Rollback

If the destination differs unexpectedly, stop before further edits and use the rollback already rehearsed against the client copy. Re-import the fresh pre-installation asset export. If that does not restore the relationships, restore the complete Superset metadata-database backup using the client's established recovery procedure.

A full metadata restore affects other Superset changes made after the backup, so schedule the installation without concurrent dashboard editing. Reporting records stay in PostgreSQL and should not be restored or replaced as part of this definition rollback.

After rollback, repeat the known hospital, date, total and filter checks. A dashboard that opens successfully is not enough to prove every relationship was restored.

Known limits and decisions

  • Clear all: official Superset 6.1.0 can retain a stale selection after Clear all and reselect. Reload after using Clear all. This package documents the limitation; it does not add a Superset patch.
  • Importer helper: the versioned helper is part of the tested installation path. It omits the database object and repairs destination references. A manual ZIP upload is not a supported installation path.
  • Time Unit choices: Month, Quarter and Year remain an installation-wide restriction on this dedicated 6.1.0 instance.
  • Supporting records view: the separate Data & records package still needs destination installation and role checks if the client accepts that workflow.
