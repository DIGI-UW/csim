Where the data comes from

Case records are entered in REDCap, uploaded into PostgreSQL, and summarized by saved queries in Superset. The dashboard displays those results. Superset calls both the uploaded tables and the calculated results datasets.

Three tables hold the uploaded data

Hospitals submit sampled case records. Each row describes a submitted case or urine-culture review, with information such as hospital, reporting month/year, collection location, symptoms, results and antibiotic treatment. Submission counts are not necessarily every urine culture performed by the hospital.

Source tableWhat it contains
UTI Individual CurrentRecords from the current collection process. Includes record ID, repeat-instance identifiers and form-completion status.
UTI Individual HistoricalHistorical records, including record ID. It does not have the Current table’s repeat-instance fields.
CSiM Hospitals and StatesThe lookup connecting hospital codes to hospitals and states. Reporting queries use it to assign records to the correct groups.

These are physical datasets: Superset entries pointing at actual database tables. Current and Historical are combined by the reporting queries. Records do not automatically move between them at year-end, and combining them does not automatically remove duplicates.

Where PostgreSQL fits

PostgreSQL stores the uploaded records. Superset stores the chart definitions, filters, layouts and saved queries separately. Registering a physical dataset in Superset does not create another copy of its records.

The supplied production connection points to database data, with tables in schema v1—a named section of that database. Its postgres:5432 address is an internal database service. Our demo uses its own database, csim_demo, with the same v1 source-table structure.

Six queries turn records into reporting results

These are virtual datasets: saved SQL queries, not additional uploaded files. They calculate results from the source tables when queried. Superset may reuse cached results until refreshed.

One aggregate row can represent many cases. Twenty submissions from one hospital in a month can contribute to one summary row. That row cannot carry a single record ID describing all twenty submissions.

The aggregate results also contain overlapping views: hospitals, states, the cohort, individual locations and “All locations.” Adding every row of the aggregate download together would double-count records.

Where to check individual records

The separate Individual records review table shows one row per uploaded record, including record ID, source, Current repeat identifiers and reporting eligibility. It includes excluded records with an explanation. It does not inherit the main dashboard’s selections.

How to see the calculation in Superset

With an editor account, open Datasets → UTI Aggregate ALL DATA → Edit → Source. The opening query combines Current and Historical. Later steps join the hospital lookup and calculate totals and rates.

Record IDs are not assumed unique across sources or repeated forms. The record-review table retains the source and repeat identifiers so cases can be distinguished. It is a separate saved query; it does not change the six reporting calculations.

How updated data reaches the dashboard

  1. Export the updated file from REDCap.
  2. In Superset, choose + → Data → Upload CSV, then the existing PostgreSQL connection and v1 schema.
  3. Use the exact existing table name, normally UTI Individual Current.
  4. Choose Replace for the existing table and upload the file.
  5. Refresh the affected chart results and check a known hospital, reporting month and submission count.

Replace replaces the table’s contents. Upload the complete set of records intended to remain in that table, not just the newly added rows.

Adding a hospital

A new hospital is a two-table update: upload its complete Current or Historical records, then add one matching row to CSiM Hospitals and States. That lookup row supplies the hospital name and state used by the reporting queries and hospital selector.

  1. Use the same hospital code in the uploaded records’ hosp_name field and the lookup table’s hosp_code field.
  2. When uploading through Superset with Replace, use a complete lookup file: every existing hospital plus the new row or rows. A file containing only new hospitals would remove the existing lookup entries.
  3. Keep exactly one lookup row for each code. No matching row hides the hospital from reporting; duplicate rows can duplicate its calculated totals.
  4. Refresh the dashboard, search for the hospital in Hospital and State, and check one known reporting month and submission count.

A saved color is optional. It affects the appearance of a comparison legend, not whether the hospital appears.

Normal uploads do not require changing the reporting queries if table names, columns and coded values remain consistent. Uploading into a newly named table does not redirect the existing queries to it.

Why an uploaded record might not appear

The aggregate query includes records with a hospital code, reporting month and year. The hospital must match the lookup. Current records must also be marked complete.

For example, a hospital 53 record can exist in PostgreSQL but remain outside the dashboard calculations because its Current form is incomplete. A valid record may also be outside the selected hospital, location or date range.

The Data & records dashboard shows inclusion and exclusion summaries. The record table explains individual exclusions. Inclusion means eligible for reporting before the dashboard selections are applied.

The Current completion rule

The saved query requires qi_asb_complete = 2 for Current records. Historical uses its own source fields and does not have this same completion check. Neither a missing lookup entry nor an incomplete form is repaired by changing a chart filter.

What moves when we update the dashboard?

A dashboard export contains definitions: charts, saved queries, layout and filter relationships. The underlying PostgreSQL records are separate. A client update must keep the client’s existing database connection and source tables, and update the intended reporting objects without creating duplicate datasets.

The separate record-review view adds one reporting dataset if included in the client package. Demo fixtures and experimental dashboards do not belong in that package.

Reporting month is different from upload date

A September upload containing July records still has July as its latest reporting month.

The reporting date is built from the source month and year, represented internally by the first day of that month. It does not establish a precise specimen-collection day, record-entry date or file-upload timestamp.

Time Period selects the reporting dates. Time Unit groups those observations by Month, Quarter or Year. A date editor accepting days does not make the underlying observations more precise.

The latest-month card uses the latest month with submissions inside the selected filters. Showing a day on that card suggests precision the calculation does not provide. An actual upload-date field would need a separate, reliable record of successful uploads.
